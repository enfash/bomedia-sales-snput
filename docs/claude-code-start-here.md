## Conventions in the code
- Schema `bomedia`. Security-definer `api_*` functions are granted only to `bomedia_financial_runtime`; sign-in functions `auth_*` only to `bomedia_auth_runtime`. New functions must be added to: `lib/server/financial-db.ts` (type, allow-list, and an explicit dispatcher line for no-argument functions), `scripts/migration/provision-auth.mjs`, `verify-financial.mjs` (and `verify-auth.mjs` for `auth_*`).
- Writes are idempotent (`prior_result` + `idempotency_requests`, one `crypto.randomUUID()` request id per unsaved edit) and write `audit_events`. PG error codes map to `FinancialError` (42501 to 403; 22023, 23514, 23505, 22P02 to 409).
- Tests: service tests inject `call`; route tests mock `next/headers`, `./postgres-auth-routes`, `./postgres-auth`; DB tests use PGlite `testDatabase()` inside `begin` with `set local role bomedia_financial_runtime`, a `failure()` savepoint helper, and `reset role` before inserting into restricted tables.
- Every page's back link is the one `BackLink` component (`components/back-link.tsx`, styled by `backLinkStyles` in `app/theme.ts`): arrow plus destination name, left-aligned with the page title. Use it for any new page; do not hand-build a back button. Pages reached from the home screen use `HomeBackLink` (same file), which shows Dashboard for the owner and Home for the cashier from the route; use it instead of a `router.back()` icon button. Only the old legacy Inventory page (to be deleted) still has one.
- Theme rules that bite (learned the hard way, details in the handoff): a button that sets its own colour or fill is fine, because the dark-mode brand colour for outlined and text buttons is a theme `variants` entry that a component's own `sx` overrides; use the exported `accent` for brand-coloured text; a numeric `borderRadius` in `sx` is multiplied by 10, so use px strings; status and tone pills come from `tonePill(tone)` (`app/theme.ts`); anything that depends on saved browser data renders a skeleton until mounted (see `useMounted` in `components/job-board.tsx`).
- Status messages that are not part of the page content (saved on this device, waiting to send, offline, confirmed) are floating toasts, never banners in the page flow: use `useFloatingNotice(id, notice)` from `components/floating-notice.tsx`, or `toast` from sonner for a one-off.
- Logic never lives in a page file: the Records and Job board logic is in `lib/records-view.ts` and `lib/job-board.ts` with tests that pin today's behaviour. Move logic first, with tests, then rebuild the view.
- A production build is checked in an env-free copy of the project (rsync without `.env*`, `cp -Rc node_modules`) so it never reads secrets or overwrites the running preview's `.next`.
- Lagos has no daylight saving; "today" means the Lagos date.
- Migrations are append-only; never edit one that has been applied. Next number is `202610120041` (037 owner approvals, 038 customer profiles and 039 expense limit are applied to the sandbox). Adding a migration also means updating `lib/schema-version.ts` (a test fails until it matches the folder).

## Correct and cancel a sale (12 Oct, built and seen running in the sandbox; uncommitted)
- Owner's rule: nothing is erased. A correction reverses the sale's old money entry line by line (the journal guard now allows a *business* reversal only while a correction sets the transaction-local flag `bomedia.business_reversal`), puts the exact net stock back on the same rolls (movement kind `reversal`), takes what the corrected sale needs (`draw_stock`, same roll order and exact cost as a sale) and posts a fresh entry (`source_type 'job_revision'`). A cancellation reverses everything and the job stays as `job_status 'Cancelled'`, amount 0, `cancelled_at/by/reason`. The old values live in `job_revisions` (before/after, stock returned/taken, who changed, who approved) and the audit log (`sale_corrected`, `sale_cancelled`). Payments stay on the job; if the new total is below what was paid the difference is customer credit (job balance goes negative; Customers nets it).
- Owner does it directly, any age (closed months are refused). A cashier may ask only when the `edit_old` rule is on (days param, default 7) and the sale is that recent; it becomes an approval request (`operation 'sale_correction'`, `changes` = the plan with before/after and stock effect). Functions: `api_sale_correction`, `api_sale_correction_preview`, `api_sale_history`; API `/api/accounting/sale-corrections` (POST, `?preview=1`, GET `?sales_id=`). Fields a correction may change: description, quantity, width, height, unit, priceKobo, materialId, businessDate (service jobs: description, quantity, date).
- Screens (`components/sale-corrections/`, helpers `lib/sale-corrections-view.ts`, styles `saleChangeStyles` in the theme): Records details (single and batch) get "Correct this sale" / "Cancel sale" (batch: per-item Correct and "Cancel the whole sale"), a Cancelled or "Corrected N times" tag and the sale's History; `CorrectSaleSheet` previews the effect live ("What this will do") and needs a reason; the owner saves at once, a cashier sends for approval (shown only when `edit_old` is on and the sale is within its days, `use-correction-access.ts`). The owner's inbox shows Correction/Cancellation cards with the field changes and the effect ("Approve and apply"); the cashier's held list and the owner's alert use the same wording. Settings → Approvals has the live "Correcting or cancelling a sale" row (days 1–90). `/api/sales` leaves cancelled sales out of every list; Records' "Show cancelled sales" asks for them with `?cancelled=only` and the totals ignore them.
- Not built yet: a Corrected tag in the Records list (only in the details), the Job board cancelled view, expense corrections and deletes (owner has not answered), a customer-credit figure on the profile.

## Correct and cancel an expense (13 Oct, built and seen running in the sandbox; uncommitted)
- Migration 041 (`202610130041_expense_corrections.sql`, applied to the sandbox): same idea as sales. A correction reverses every money entry of the expense still in force (`expense_open_entries`) and posts the corrected one (`source_type 'expense_revision'`); a cancellation reverses them and the expense stays as `Cancelled` with amount 0. Old values live in `expense_revisions` and the audit log (`expense_corrected`, `expense_cancelled`). A paid expense keeps the cash that left: what is no longer an expense is held in new account `1300` "Paid out, to be recovered"; a paid expense cannot go up. An unpaid expense just changes what is owed; `expense_is_payable` was redefined to follow the entry in force. Expenses from before the books (no money entries) are refused.
- Owner changes directly; a cashier may ask only for an expense they logged, within the `edit_old` rule's days (one rule now covers sales and expenses), held as `approval_requests.operation 'expense_correction'`. Functions `api_expense_correction`, `api_expense_correction_preview`, `api_expense_history`; API `/api/accounting/expense-corrections` (POST, `?preview=1`, GET `?reference=`). `/api/expenses` leaves cancelled expenses out; `?cancelled=only` returns them.
- Screens: `components/expense-corrections/` (correct and cancel sheets, effect box, history), wired into `ExpenseDetailsSheet` (owner Expenses page) with a "Show cancelled expenses" chip and Cancelled badge; inbox, held list and alerts handle `expense_correction`.
